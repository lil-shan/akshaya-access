## Findings, highest severity first

The observations labelled "live" or "rendered" were exercised. Other findings follow the cited code paths; no real credentials, citizen recordings, or payment services were used.

### Blockers

1. **Blocker | voice | `voice/parsing.py:63-67`, `voice/engine.py:66-75,83-94`. A correction counts as consent.** I ran the parser: `not correct` -> `True`; `I am not sure it is correct` -> `True`; `I want to correct the number` -> `True`. It looks for any affirmative token, not an affirmative answer. Both read-backs use it, so the backend receives genuine boolean `true` even when the citizen disputed the number or amount. Accept only whole, unambiguous affirmative replies in each supported language. For mixed or qualified replies, use the existing retry/decline path. Test that no fetch or payment starts on a correction.

2. **Blocker | backend | `backend/app.py:43-45,125-126,258-260,327-329`. Secrets and unmasked phone numbers can be persisted in free text.** A transcript or handoff note containing an ordinary short PIN, six-digit OTP, or domestic phone number is outside the redactor's 12/16-digit patterns. The value goes into SQLite and comes back through `/calls`; both language fields are displayed. Different groupings or spoken words can also defeat the Aadhaar/card assumption. Masking `caller_phone` on create and forbidding extra JSON keys do not protect these paths. Reject or replace unsafe text *before* storage/response; prefer known-safe transcript meanings for citizen turns, preserve the legitimate consumer read-back, and test both returned JSON and database contents.

3. **Blocker | voice | `voice/engine.py:159-177`, `voice/parsing.py:49-60`, `voice/sim.py:29-39,62-70`. Redaction happens too late or not at all.** A PIN volunteered in grouped number words the digit parser does not understand can leave fewer than four recognized digits: the original sentence is then posted and printed. Conversely, exactly 13 recognized digits while collecting exempt the *whole utterance*, even if it contains unrelated sensitive text. In audio mode the raw WAV is already recorded and sent to remote STT before this check. Store/show only a normalized expected answer or a safe placeholder for unrecognized/sensitive speech; do not log raw input because its digit count looks acceptable. Keep audio synthetic-only until the team can make an honest capture/privacy guarantee. The no-listening rule during the bank step itself is correctly implemented.

4. **Blocker | backend | `backend/app.py:265-271`; consumers: `frontend/src/components.tsx:24-26,149`. The caller of `/end`, not the payment service, can decide the displayed financial outcome.** A mistaken `paid` outcome with a pending payment (or no payment) is stored unchanged. The payment card can then say pending/Not started while the call list says paid. Derive payment outcomes at close from the stored service result, or reject inconsistent ones; never infer success. Preserve any historical *at-end* outcome separately in wording, not as an alternative current payment status. Cover missing, pending, failed and confirmed payments.

### Major

5. **Major | voice | `voice/sim.py:77-85`, `voice/engine.py:143-157`. In audio mode an unheard read-back is treated as delivered.** A synthesis error is printed and swallowed; nonzero `aplay` exits are ignored. The transcript already says the prompt was spoken, and the next citizen turn can still authorize payment. Require successful playback of the opening and read-backs before listening for consent; on failure stop the payment flow and end or hand off safely. Test a failed speaker/TTS locally, without a paid API call.

6. **Major | backend | `backend/app.py:58-66,168-178`, `backend/tests/test_api.py:184-192`. Validation errors can reflect the very data rejected.** FastAPI's default 422 includes Pydantic's `input` in the error details. An unexpected sensitive field can be echoed to the client; a missing required property in a call object can include the submitted object, including the raw caller number. The tests check only the status. Return a small safe error code/location, not submitted input or arbitrary field text. Test with harmless sentinels that neither error bodies nor logs contain the rejected values. Also constrain `language` to a language tag rather than persisting arbitrary text (`backend/app.py:238-241`).

7. **Major | backend | `backend/app.py:204-208,218-220,282-295,298-314`. Confirmation is not tied to the currently selected bill.** Changing from fixture A to B changes `calls.bill_id`, but A remains eligible with its old confirmation. A stale request can start payment for A while the detail view shows B; a later fetch of A can also resurrect its old amount confirmation. Use the call's current bill for both guards, clear consent on a new selection, and disallow changing the payable bill once collection starts. Test corrections between the two payable fixtures; no new public endpoint is needed.

8. **Major | voice | `voice/engine.py:37-49,96-111`, `voice/sim.py:105-109`. Interruptions can leave a ghost call or invent a pending result.** A backend error after call creation escapes before `/end`; after a transient status-read failure the dashboard can keep selecting an active call that the simulator has left. Ctrl-C anywhere in `paying` assigns `payment_pending` from the state name, even before start succeeds or after a final bank result was received. Track the actual payment and last observed service result. On exit make a best-effort close or handoff when reachable; if status is unavailable, say that rather than asserting a bank result. Don't retry a payment start to recover.

9. **Major | voice | `voice/lines.py:70-75,84-87`, `voice/backend.py:38-39`. Two spoken promises exceed the prototype.** The pending script says "You can call back later to check"; the next call starts fresh and cannot look up that payment. A handoff says "They will call you back"; the actual result is only a queued case with a masked contact. State only the observed pending status or queued case and its identifier. Remove the promises rather than adding callback infrastructure or retaining an unmasked number.

10. **Major | contracts | `contracts/README.md:28-36`, `backend/app.py:34-37,302-305`, `backend/tests/test_api.py:144-149`. Duplicate-payment scope is unresolved.** The backend task says the same bill must not start twice; the implementation and test enforce this only *within one call*. Live, the same fixture bill produced three separate payment IDs in three calls. That's useful for replaying a demo, but a redial while the first attempt is still pending can also initiate another collection. Specify the intended retry rule (at least for an outstanding pending payment) versus deliberate fixture replay. Do not describe the current guard as bill-wide.

11. **Major | frontend | `frontend/src/components.tsx:24-26,111-115,149`. Late confirmation leaves two apparently current outcomes.** I let voice time out, then used the real bank control. The rendered panel said `confirmed` with `Reference SIM123PAY-000001` **and** `Outcome: payment pending`. Both facts are useful at different times. Label the latter "At hang-up: pending" in the list/panel, or show only the authoritative current status there; keep the spoken pending transcript unchanged.

### Minor

12. **Minor | frontend | `frontend/src/components.tsx:78-90`. A zero bill still awaits confirmation after hang-up.** The real zero-due response rendered `Awaiting citizen confirmation ... Not started Outcome: nothing due`. The voice flow intentionally skips confirmation here. For a zero bill, display "Nothing to pay"; for a declined/ended bill, distinguish "Not confirmed" from "Awaiting".

13. **Minor | voice | `voice/engine.py:96-102`, `voice/sim.py:102-105`. The configurable polling deadline is not a wall-clock deadline.** The loop counts only sleep, omits HTTP time and sleeps a full interval even when less time remains. A zero interval never advances `waited`; a negative interval or invalid float can raise an exception. Validate finite settings before creating a call, use a monotonic deadline and bound each remaining wait/request. `voice/tests/test_engine.py:124-135` checks scheduled sleeps, not elapsed time.

14. **Minor | backend | `backend/app.py:74-78,198-202,254-269`. An `ended` state event does not end the call.** It sets `state='ended'` but leaves `ended_at` null, so the active filter still returns it, the frontend says `live`, and tool writes are still allowed. Reserve that terminal transition for `/end` (and document it) or route it through the same close logic. Ordinary `done`/`handed_off` intermediate events need not close the call.

15. **Minor | voice | `voice/engine.py:59-63,115-119,164-176`, `contracts/tools-api.yaml:133-146`. Unsupported service requests are misclassified.** A request for a pension certificate is treated as zero consumer digits; repeating it queues `number_unclear`, not `unsupported_service`. Route recognized out-of-scope requests to the existing handoff reason, leaving ambiguous numbers on the existing two-attempt path. No general intent engine is needed.

16. **Minor | frontend | `frontend/src/mock/mock.ts:35,45,68-79`. The fallback demo omits parts of the trust flow.** The mock opening omits AI identity and the no-secrets warning, and "is [the bill] correct?" becomes authorization to start payment rather than asking permission to pay. It also ignores the supplied payment ID and leaves the final state `done` with `ended_at` populated, unlike the real API. Align the small mock's prompts, ID check and terminal snapshot with the observed flow; keep the visible mock/SIMULATED labels.

17. **Minor | voice | `voice/lines.py:3-11,38-48`, `voice/engine.py:78-85`. Malayalam audio labels the payment as simulated, but not the bill.** The bill disclosures are in `text_en`; these read-backs are spoken in Malayalam only. Add the simulated KSEB bill disclosure to the Malayalam opening or bill lines. The live text transcript's English labels and the frontend bill/payment badges are fine.

18. **Minor | backend | `backend/smoke.sh:1-5,9-21`. The smoke command can finish green after failure.** It prints rather than checks most statuses/values, does not fail fast, and ends with a successful `echo` even if earlier requests failed. Readiness can also come from another server already on the port. Use an isolated DB, verify the child owns the run, assert expected statuses/outcome and clean up via a trap. The pytest suite does make substantive assertions; this issue concerns the smoke wrapper.

19. **Minor | contracts | `contracts/tools-api.yaml:59-68,133-148,184-198`. Request and error schemas do not fully describe actual validation.** Unknown request keys are allowed by the schema but rejected by the backend; optional `text_en`, `outcome` and handoff `note` accept explicit null in the backend but not in those request schemas. Handoff documents only 201, but an ended call returns 409 `call_ended`. Document the stricter no-extra-fields rule, decide omit vs null, and list applicable error responses. Keep response `Event` extensible with `seq` and `at` when closing the input schema.

20. **Minor | voice | `voice/README.md:66-74`, `.devin/roles/shared.md:13`. The required `.env.example` is absent.** Someone following the shared setup convention has no template for the audio key or polling options. Provide placeholders only. No real key was needed for this review.

One-shell replay of the four required live flows (Bash; same HTTP operation as the frontend button). It checks readiness, waits for an actual poll, prints every call detail and stops its own server:

```bash
(
  set -euo pipefail
  p=/home/shan/devin

  export PYTHONDONTWRITEBYTECODE=1 BACKEND_DB_PATH="$t/run.db" BACKEND_URL=http://127.0.0.1:8000

    if [[ $f == */happy_path.txt ]]; then
```
